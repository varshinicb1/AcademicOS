Turn on the scheduler and error alerts

For the AcademicOS backend on Google Cloud, project vidyuthlabs, region asia-south1 (Mumbai). About 10 minutes. Nothing here needs a code change or a redeploy.

What the scheduler does. Every 5 minutes it calls the backend once. The backend then sends what is due: homework due tomorrow (16:00), overdue homework (09:00), the teacher's evening digest (18:00), the principal's morning alerts (08:00) and Monday digest (07:00), marking and exam reminders, cover escalation, and retries of question bank webhooks. Each job runs once per day or week however often it is called, so calling every 5 minutes never sends anything twice.

Without it, these run only while someone is using the app (at most every 5 minutes), so a 07:00 digest waits until the first person signs in.

Before you start

  • Open PowerShell on the computer where gcloud is signed in as the project owner (gcloud auth list shows the account).
  • Do it when no deploy is running (GitHub, Actions tab: nothing in progress).
  • Cost: Cloud Scheduler gives 3 jobs free per billing account; this uses 1. Uptime checks are free at this volume.

1Switch Cloud Scheduler on

gcloud services enable cloudscheduler.googleapis.com --project vidyuthlabs

Takes up to a minute. It answers Operation ... finished successfully.

2Make the scheduler key

A random key that only the scheduler and the backend know. This block creates it in Secret Manager and never prints it.

$b = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
$key = ($b | ForEach-Object { $_.ToString('x2') }) -join ''
$tmp = New-TemporaryFile
[System.IO.File]::WriteAllText($tmp, $key)      # written with no newline at the end
gcloud secrets create acos-cfg-cron-key --project vidyuthlabs --replication-policy automatic --data-file $tmp
Remove-Item $tmp; Remove-Variable key, b

If it says the secret already exists, replace gcloud secrets create acos-cfg-cron-key ... --replication-policy automatic with gcloud secrets versions add acos-cfg-cron-key --project vidyuthlabs --data-file $tmp and run the block again.

3Give the backend the key

--update-secrets adds this one key and keeps every other setting (Sarvam, Composio, Google sign-in). Do not use --set-secrets, which would drop them.

gcloud run services update academicos-backend --region asia-south1 --project vidyuthlabs `
  --update-secrets "ACOS_CRON_KEY=acos-cfg-cron-key:latest"

About a minute. Every later deploy keeps it on its own: the deploy wires in each optional secret that exists.

4Create the job

$key = gcloud secrets versions access latest --secret acos-cfg-cron-key --project vidyuthlabs
gcloud scheduler jobs create http acos-automations --project vidyuthlabs --location asia-south1 `
  --schedule "*/5 * * * *" --time-zone "Asia/Kolkata" `
  --uri "https://academicos-backend-2eskom55ta-el.a.run.app/api/v1/automations/run" `
  --http-method POST --headers "X-Cron-Key=$key" `
  --attempt-deadline 120s --max-retry-attempts 1 `
  --description "AcademicOS reminders, digests and webhook retries"
Remove-Variable key

5Check it works

gcloud scheduler jobs run acos-automations --project vidyuthlabs --location asia-south1
Start-Sleep -Seconds 30
gcloud logging read 'resource.type="cloud_run_revision" AND httpRequest.requestUrl:"/automations/run"' `
  --project vidyuthlabs --limit 3 --format "value(timestamp, httpRequest.status)"
You seeMeaning
200Working. Nothing more to do.
404The backend does not have the key yet. Run step 3 again and wait a minute.
401The key in the job is not the one the backend has (for example the key was replaced after the job was made). Delete the job (gcloud scheduler jobs delete acos-automations --project vidyuthlabs --location asia-south1) and run step 4 again.
PERMISSION_DENIEDThe signed-in account is not an owner or editor of vidyuthlabs.

Each run's results (which jobs ran and how many people each notified) are also listed for a signed-in principal by the API at GET /api/v1/automations/status.

Optional: get an email when the site is down

6Uptime checks (every 10 minutes, from 6 places)

gcloud monitoring uptime create "AcademicOS backend" --project vidyuthlabs `
  --resource-type uptime-url --resource-labels "host=academicos-backend-2eskom55ta-el.a.run.app,project_id=vidyuthlabs" `
  --path /health --protocol https --period 10 --timeout 10 `
  --matcher-type contains-string --matcher-content '"status":"ok"'

gcloud monitoring uptime create "AcademicOS website" --project vidyuthlabs `
  --resource-type uptime-url --resource-labels "host=vidyuthlabs.web.app,project_id=vidyuthlabs" `
  --path / --protocol https --period 10 --timeout 10

7Send the alert to your email (Console, 3 minutes)

  1. Open Monitoring, Alerting, Edit notification channels. Under Email, Add new: your address, display name "AcademicOS owner".
  2. Open Uptime checks. For each of the two checks: the three-dot menu, Add alert policy, choose the email channel, Create policy.

8Email on server errors (Console, 3 minutes)

  1. Open Logs Explorer and paste this query, then Run query: 
    resource.type="cloud_run_revision"
resource.labels.service_name="academicos-backend"
httpRequest.status>=500
  2. Actions, Create log alert. Name it "AcademicOS server errors". Time between notifications: 30 minutes. Choose the email channel from step 7, Save.

You then get at most one email per 30 minutes while errors happen, with a link to the failing requests.

Undo

gcloud scheduler jobs pause acos-automations --project vidyuthlabs --location asia-south1    # stop for now
gcloud scheduler jobs delete acos-automations --project vidyuthlabs --location asia-south1   # remove
