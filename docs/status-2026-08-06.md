# AssessmentOS — Status as of 2026-08-06

> **Dated snapshot — 6 weeks old.** Kept as a record of what had been verified
> on that date, not as current status. For the current picture see
> [`REQUIREMENTS_BY_LAYER.md`](REQUIREMENTS_BY_LAYER.md) (per-layer status and
> verification depth) and [`system-review.html`](system-review.html).

Honest snapshot of what exists, what's verified, and what isn't, for the
DSG (Deccan Springs Global School) pilot. "Verified" means: called with real
data through the actual running backend/app and the output was inspected —
not "the code looks right."

## Working end-to-end, verified today

**Assessment Designer (Windows desktop app)**
- Question bank: 4,143 questions extracted from real CBSE board papers
  (Class X Science/Maths/Social Science/English, Class XII Physics/
  Chemistry/Biology/Maths/Accountancy/Business Studies/Economics/History/
  Geography/Political Science/English).
- Difficulty labels now correctly track mark value (5-mark questions →
  "hard", not capped at "medium" by a Bloom-level field that was always
  empty). Verified: Science 31 hard, Math 92 hard, matching the 4-5 mark
  question counts.
- Answer keys: 1,819 CBSE marking-scheme PDFs parsed and joined to the
  question bank by (subject, grade, paper code, question number). 232/429
  Science questions and 442/913 Math questions carry an official answer.
- MCQ auto-scoring works off that key: a correct answer scores `fullCredit`,
  wrong scores `noCredit`, both with real confidence and marking-point trace
  — verified via the running Evaluate screen and direct API calls.
- Corrupted source text no longer reaches a printed paper: ~765 Math MCQs
  with PDF-flattened fraction options (numerator/denominator split across
  lines, losing the value) are now filtered out rather than shown broken.
  A separate bug that misread the trig variable "A" as the Ampere unit
  (corrupting "sec²A" into "sec²A⁹") is fixed.
- Missing minus signs: traced to some CBSE PDFs drawing the minus sign as a
  thin vector rectangle instead of a text character — recovered by matching
  drawn rectangles to adjacent words and splicing the sign back in. Re-ran
  across all 367 question papers in the corpus.
- **School branding is now real, not cosmetic-only.** Found and fixed the
  actual reason branding never appeared on an exported paper: the paper-
  generation endpoint accepted a `template` in the request and then never
  stored it, so every export silently fell back to no branding regardless
  of what a school configured. Deccan Springs Global School's template
  (name, tagline, brand color) is now the default for `school_1` and
  verified rendering correctly on an exported paper PDF.
- Font fix: the exported-PDF font (Arial) was missing the Unicode subscript
  digit block, so chemistry formulas like "Al₂O₃" printed as tofu boxes.
  Switched to Segoe UI, which has full coverage — confirmed with fontTools
  against the actual font file, then confirmed visually on a re-exported
  paper.
- Practice-test generation (`/practice/generate`) and class/school insights
  (`/insights/class/*`, `/insights/school/*`) — pre-existing, reconfirmed
  working against real data this session.

**New this session, verified against real data:**
- `llm_evaluate.py` — Sarvam **105b** evaluates one answer at a time with a
  CBSE-spot-evaluation-style prompt ("liberty of correction": credit a
  correct alternate method, don't zero out a correct method for one
  arithmetic slip, don't penalize phrasing). Verified against a real Science
  question: an answer worded completely differently from the marking scheme
  ("gas bubbles came out" vs. the scheme's "evolution of gas") still got
  full, correctly-reasoned credit — genuine semantic matching, not keyword
  overlap. Also verified it correctly gives **zero** credit to an answer
  that's simply off-topic, and both MCQ branches (right/wrong option).
  Needed 4000 max_tokens, not the ~500-1000 that would seem to suffice —
  sarvam-105b is a heavy internal-reasoning model and a tight budget
  silently truncates the JSON output before it's ever written.
- `imaging.py` — mobile-capture preprocessing: OpenCV document-edge
  detection + perspective correction, falling back to "keep the full frame"
  when no confident page edge is found (never guesses a crop that might cut
  off an answer), plus CLAHE lighting correction for shadowed/uneven photos.
  Verified mechanically against a rendered page image (correctly detected
  "no page edge in a pre-scanned image" and used the safe fallback; the
  lighting-correction step produced a valid output image). **Not yet tested
  against an actual angled phone photo** — no such photo was available this
  session; the fallback path is what would run on a bad detection and is
  the one actually exercised so far.
- `report_pdf.py` — branded per-student progress report: overall mastery,
  concept-by-concept table (status/accuracy/evidence count), and a specific
  recommended action per weak concept (not "study harder" — e.g. "accuracy
  is inconsistent on this concept, which usually means one specific step is
  wrong rather than the whole concept; review recent answer sheets
  together"). Verified end-to-end: graded a synthetic student, generated
  the report through the real `KnowledgeStore`, rendered it, confirmed DSG
  branding and correct data on the page image.

## Explicitly NOT done — do not assume these work

**The mobile scan-and-grade app the school actually asked for is not built.**
What exists is the *backend* pieces it would need (`imaging.py`,
`llm_evaluate.py`, the existing `scan.py`/`vision.py` OCR pipeline) —
verified individually, never wired together into one flow, and there is
**no mobile UI** for any of it:
- No camera-capture screen (teacher selects test + student, photographs
  pages, taps done).
- No Tinder-swipe review UI (approve/edit each AI-scored answer).
- No "save raw booklet as PDF" on-device.
- No corrected/annotated PDF export after teacher review.
- The existing Flutter app has an `android/` and `ios/` platform scaffold
  (so this is not starting from zero — it's the same codebase, not a
  separate app to build) but nothing mobile-specific has been added to it,
  and nothing has been built or run on an actual Android device or
  emulator this session.

Building and testing that full flow — camera capture through corrected-PDF
export — is a substantial remaining project, not a small addition. It should
be scoped and built as its own piece of work, not assumed complete because
its backend dependencies exist.

**Accuracy claims:** nothing in this session supports a "100% accuracy"
claim for handwriting OCR + AI grading, and none should be made to the
school. What's true: Sarvam Vision was validated earlier against real
evaluated CBSE scripts (`cbse-model-answers/`, examiner tick marks as
ground truth) and got final numeric answers right; the LLM evaluator gives
real semantic credit in the cases tested here. Neither claim adds up to a
measured accuracy number on a real batch of scanned, handwritten answer
booklets — that number does not exist yet and would need a real pilot batch
to produce honestly.

## Known gaps carried forward

- Answer keys only exist where a marking scheme was successfully matched by
  paper code — most non-Science-X subjects and most years are not covered
  yet (706 objective answers total across the whole corpus).
- Chapter tagging (used for syllabus coverage and weak-concept naming) is
  Science-only; other subjects show "Unmapped" for chapter-level analysis.
- 283 corpus "documents" are 1,208-byte failed-download stubs, not real
  PDFs, and ~95 scanned (no text layer) papers still need OCR.
- 1 PDF failed the latest re-parse (corrupted file) — not investigated.
- Graded answer sheets live in server memory (`_papers`, `_paper_templates`,
  `_graded` in the route modules) and are lost on backend restart. Fine for
  a pilot on one machine; needs real persistence before this runs
  unattended or on a server that restarts.
