System review · prepared for technical due diligence AcademicOS · 16 Sep 2026

What the backend does, what the frontend does, and where they disagree.

AcademicOS is an evidence-grounded academic operating system for CBSE/NCERT schools: a FastAPI backend over an ingested curriculum corpus, and a Flutter client built as two sub-products — an offline Android app and a cloud web app. The backend runs as two independent releases. This review states what each part does as built today, and marks its own claims by how they were established — measured, read from source, or asserted by prior documentation and not re-verified here.

Orientation — what actually exists

AcademicOS is two client sub-products and two backend releases. These are frequently conflated in the project's own documentation and code comments, so they are separated here first — everything after this table depends on the distinction.

Two consequences worth stating plainly. A defect reported against Mobile cannot be fixed by redeploying any backend — there is no backend in that path. And the GCP release is not an upgrade of the Render release: both serve the same source tree, they coexist, and switching between them is an environment-variable change rather than a migration.
01measured

Backend

A curriculum engine, an assessment designer, and an evaluation pipeline — behind one API.

24,500 lines of Python across 139 modules, exposed as 122 operations on a single FastAPI application. It is the half of the system that holds knowledge; the client is largely a view onto it.

What it actually does

  • Ingests a corpus with provenance. Official PDFs (CBSE papers, NCERT textbooks, marking schemes, circulars) are parsed with native text extraction raced against OCR. Every chunk and graph node carries document_id, page_number, bounding_box, method and confidence. Documents below a confidence floor are held back rather than silently admitted.
  • Models the curriculum as a substrate. A canonical hierarchy — Board → Academic Year → Grade → Subject → Unit → Chapter → Topic → Subtopic — plus the operational calendar: working days, term dates, block holidays, period length, subject period allocations and weekly timetable slots.
  • Designs examinations. A deduplicated question pool extracted from real board papers, semantically tagged to curriculum nodes, assembled into blueprints balanced by Bloom level, question type and difficulty — then rendered to PDF question papers and marking schemes, including parallel sets (A/B/C) with internal-choice swapping.
  • Evaluates answer scripts. Multi-page capture, perspective rectification, OCR, itemised grading with teacher review, and an append-only audit trail.
  • Tracks learners. FSRS spaced repetition, knowledge-state estimation, mastery and misconception modelling, and prerequisite mining over the curriculum graph.

How it is stored

Seventeen SQLite stores hold operational state — per the repository's own operating guide — and eleven of them have a remote durability backend so they survive the ephemeral container disk that both Render and Cloud Run provide. As of this session that remote backend is abstracted: every store resolves it through one factory that prefers Cloud SQL Postgres when configured and falls back to Supabase otherwise, with local SQLite as the last resort. The precedence is an environment-variable change, and reversible in both directions.

Known constraint. The container filesystem is not durable. If deployed without Cloud SQL or Supabase credentials configured, each of up to three instances keeps its own SQLite file and they diverge — the failure is silent, not loud.
02source-read

Frontend — two sub-products

One Flutter codebase, two products: a cloud web client, and an Android app that needs no server at all.

64,700 lines of Dart across 24 screens, targeting web and Android from a single codebase. The distinction that matters: the Web sub-product is a thin client that needs the backend for every action, while the Mobile sub-product runs the paper-generation and evaluation logic on the device and never contacts a backend at all.

What each role sees

RoleScreens and capability
TeacherSyllabus browser by subject and grade; daily planner and timetable; question bank; assessment create → review → approve; paper export and email delivery; practice sessions; Scan & Grade capture; progress and gap analysis.
PrincipalSchool admin console — roster, master calendar grid, coverage and pace reporting, drag-and-drop sequence reordering, reschedule (push/adjust), calendar setup; school-level insights; paper approval.
StudentPersonal schedule in day, week, month and overview views; syllabus completion; mastery dashboard; practice.
ParentDedicated portal: child syllabus completion, daily attendance and lesson tracking, growth-mindset guidance and concept scaffolding.

How it is built

  • Routing — go_router, 24 named routes with deep-link paths.
  • State — effectively StatefulWidget-driven (27 stateful screens, one Bloc). The Bloc dependency is present but not the organising pattern.
  • Wiring — get_it service locator; repositories over API clients.
  • Transport — dio, against a build-time base URL (ACADEMICOS_API), defaulting to localhost:8010/api/v1.
  • Local storage — hive, encrypted, holding the offline assessment, evaluation, mastery, consent and scan records.
  • On-device processing — ML Kit text recognition for OCR, and client-side PDF generation for exports.

How the two sub-products diverge

ACADEMICOS_OFFLINE=true — set only by the standalone Android build — swaps two objects in the service locator. LocalApiClient and LocalPillarApi subclass the HTTP clients and reimplement paper selection and evaluation against the bundled corpus, with identical method signatures and response shapes. Every repository, use case and screen above them is unmodified between the two builds — which is why 24 screens can serve both products without branching.

Why this matters. Low-connectivity schools are the deployment reality, so the Mobile sub-product is a genuine asset rather than a nice-to-have. It is also the largest unshared maintenance surface in the codebase: the offline engine must be updated by hand whenever the server contract changes, and nothing detects that drift automatically.

The seam

The frontend and backend were written independently. They do not fully agree.

This is the single most important thing to understand about the system as it stands. It is not currently breaking anything — but it is a trap, and it has now been measured rather than estimated.

Why it is not a live outage

The screens drive PillarApi almost exclusively, and every ApiClient method the user interface actually calls maps to a route that exists (getAssessment, getPaper, approveAssessment, exportPaper, quickGeneratePaper, updateAssessment). No screen references the mastery, analytics, report, notification, answer-sheet or evaluation repositories at all.

So the 46 dead endpoints are latent: roughly 800 lines of repository layer, wired into dependency injection and covered by tests — that would 404 the moment somebody connected a screen to them. Two further consequences follow from the same root cause:

  • The offline implementation had eleven silent stubs — getMisconceptions() ⇒ [], finalizeEvaluation() ⇒ nothing. A teacher on the Android build was shown "no misconceptions" and had no way to know it meant "not implemented". Those now raise, so empty and unsupported are distinguishable. fixed this session
  • A contract test now fails the build when a new frontend call has no backend route, and also when an allowlisted gap is fixed but left on the list — so the debt cannot silently grow or silently rot. added this session
04104 secured

Security posture

Authentication was enforced but undocumented. It is now both — and 15 routes are newly gated.

The most consequential finding was not a missing check but an invisible one. get_current_user read the Authorization header as a plain parameter rather than a declared security scheme, so FastAPI published securitySchemes: None — the generated API documentation advertised all 122 operations as public, including 89 that return 401 on first call. Any integrator working from the spec would have built the wrong thing.

Legacy surface gatedAll ten /v1/* routes — corpus search, agents, graph, revise/plan/solve — now require a caller.
Impersonation closed/ingest/school-documents took school and uploader identity from the request body. Any anonymous caller could file a document against any school and attribute it to anyone. Identity now comes only from the session.
Exactly what remains openThree auth endpoints, two health probes, and thirteen read-only curriculum-reference GETs the client needs before login.
Honest residual. School-scoped isolation is enforced on the routes that were audited, but three stores — papers, practice sets, scan sessions — still carry no school_id column, so the export and backup paths cannot scope them. That is the largest outstanding correctness gap and is unchanged by this session.

Build & run — two releases

The Render release is live. The GCP release is written, reviewed, and has never run.

Both releases build the same backend from the same commit, and both are gated by the same test suite. They differ in compute, registry, data backend, secrets — and, most importantly, in how much has actually been proven.

The GCP release pipeline

Shown here because it is the unproven half. It is keyless by construction: GitHub's OIDC token is exchanged for short-lived credentials scoped to one repository and one branch, so no service-account key exists and there is nothing to rotate or leak. 

push to master
   │
   ├── test       1,170 backend tests           ← a red suite deploys nothing
   │
   └── backend    GitHub OIDC ──► Workload Identity Federation ──► no stored keys
                  │                 (nothing to leak, nothing to rotate)
                  ├── Cloud Build ──► Artifact Registry      (~650 MB image, layer-cached)
                  └── Cloud Run   ──► /health polled until it answers
                                     min-instances 1 → users never see a cold start

Application secrets live in Secret Manager and are injected at deploy time. The owner's involvement is a single idempotent bootstrap script — APIs, registry, service accounts, the federation trust, secrets, Cloud SQL with backups, storage buckets and a budget alert — with a --check mode that reports the three conditions genuinely requiring the account owner (billing disabled, an org policy blocking Cloud SQL, missing API permissions) before anything is created.

What has not been proven. The GCP bootstrap has not been run. Cloud Build, Cloud Run, Workload Identity Federation and the frontend deploy are unexecuted; gcloud flag validity is asserted, not confirmed. The measured numbers elsewhere in this document come from local execution against real Postgres and a real Flutter build — not from the cloud environment these scripts target.
06verdict

Assessment

What a CTO should weigh.

Strengths

  • The knowledge model is the moat, and it is real. Provenance-tracked ingestion, a canonical curriculum hierarchy, and a question pool drawn from authentic board papers with marking schemes — not generated content.
  • Verification habits are better than typical. 1,170 backend tests, a route-inventory contract test, golden PDF checks, and a culture of measuring rather than assuming — every number in this document is reproducible.
  • Offline capability is genuinely differentiated for the target market.
  • The deployment path is modern and credential-hygiene correct — keyless, least privilege, secrets in a manager, one-time owner involvement.

Findings, by severity

  • High
    Two systems, one interface, neither complete. The HTTP client targets 46 endpoints that do not exist; the offline client silently no-op'd eleven methods. The UI happens to only exercise the working subset. This is architectural drift that will resurface the moment a new screen is wired up. Pinned by a ratchet; not yet resolved.
  • High
    School isolation is incomplete. Three of the durable stores carry no school_id, so cross-school scoping cannot be enforced on them and the export path cannot cover them. This is a compliance exposure under DPDP, not merely a bug.
  • High
    The production deployment is unproven. Written, reviewed, syntax-validated — never executed. Treat the first real run as the beginning of the integration work, not the end.
  • Medium
    Durable state depends on configuration that fails silently. Deploy without Cloud SQL or Supabase credentials and each instance keeps a private SQLite file. Nothing errors; the data simply diverges.
  • Medium
    A 6.8 MB question bank ships inside the web bundle. Downloaded by every browser, when the same data is available from the API. Removal needs a build-flag decision first, because the offline build legitimately requires it locally.
  • Low
    Two API generations coexist. The /v1 pillar surface is now gated but remains exposed and unused by the client. Retirement is a cleanup, not a risk.

The question worth asking

The backend is a serious, well-tested curriculum and assessment engine. The frontend is a broad client that has grown a parallel, partially-fictional view of that engine. The decision in front of the team is not technical: it is whether to delete the fictional surface and narrow the product to what genuinely works end to end, or to build the 46 missing endpoints and honour the interface the client already declares. Both are defensible. Doing neither is how the drift compounds.
