This is the first audit on the **v3 scorecard** (`docs/product-scorecard-v3.md`, adopted and merged in #55 before
this audit ran). It measures the three-app product of `docs/REQUIREMENTS.md`: grades 1-10, the web console, the
teacher app, the student app with parent mode, the scheduling engine, notifications and the question bank API.
It is **not comparable** with the v2 numbers (the last v2 audit was 60.5 at `09649eb`), which measured only the
web-first, classes 6-10 product.

  #54 (classes 1-10 paper generation, the new bank sources) and the bank-pipeline outputs.
- **Local runs:** signed-in flows ran on that commit's code (the release worktree, read-only, `PYTHONPATH` pinned to
  it), through FastAPI TestClient harnesses that replay the web app's exact requests, on the served bank. Each run
  used a fresh temp data root, and no storage variable was set.

- **Gates:** cited, not re-run:
  - backend 4,154 passed / 113 skipped / 3 xfailed on `63387c7`, plus #53's test-only fix (1 failure → 0);
  - Flutter 520 passed, 7 infos.
- **Rubric:** as written. When evidence was weak, the item was scored down. No teacher or student app build exists,

## Fix first: defects that break trust

Items 1-3 were re-checked in the code by the maintainer's session. Items 4-6 are the auditors' reproductions, in
their sections below.

1. **N-67-2 (privacy): one school sees others' students.** `/insights/school/{own id}` builds its counts, mastery,
   weakest concepts and interventions from every school's graded students. It uses `graded.all_student_ids()` and
   `graded.assessment_count()` with no school filter (`assessment/pillar_routes.py:1160-1164`), and the live web's
   Principal page calls it.
2. **N-2-1 (integrity): any teacher can approve their own paper.** `PATCH /assessments/{id}/status` needs only staff
   and accepts `principalApproved` without an approval audit row (`assessment/routes.py:969-986`). A `PUT` of a draft
   can carry the status too.
3. **N-2-2 (integrity): any teacher can delete an approved, locked paper, unaudited.** See `routes.py:961-966`.
4. **N-67-1 (access): a delegated admin's class, section and subject limits are never enforced.** A class 6
   timetable admin can re-solve the whole school; a class 6 reports admin sees class 10 names
   (`auth_routes.py:248-251`).
5. **N-9-1 (privacy): automation run status is readable across schools.**
6. **N-8-1: two delivery passes running at once send every push and email twice.** The same race is in #51's SMS
   draft.

## New defects

### Area 8

1. **N-8-1 (major; NTF-1, NTF-3). Concurrent deliveries send every push and email twice.**
   - Where: `notifications.py:373-377` starts a delivery thread for every `notify()`. `routes.py:229` runs `deliver_due()` inside `GET /notifications`. `deliver_due` (`notifications.py:386-419`) reads the pending rows, sends, and only then writes each status, with no claim on the row.
   - Repro, `area89/h_double_send.py`: 3 pending notifications and two `deliver_due` passes at once give **6 pushes, 3 of them duplicates**.
   - In production, one leave decision calls `notify` 1 + N times, for the decision and each substitute. That starts that many threads at once.
   - Effect: once FCM or SMTP is switched on, people get the same push or email two or more times.
