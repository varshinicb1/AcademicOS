# R-A1 Plan: Move CurriculumStore and OperationsStore to Cloud SQL Postgres

> **Superseded by `docs/r-a1-cutover.md` (October 2026).** The engagement that wrote this plan ended
> on 15 October; R-A1 was built in-house. The translation approach below was kept, at the connection
> rather than in four helpers: about 110 call sites use the SQLite connection directly. The cutover
> runbook says how each of the six findings in issue 143 was resolved, with the tests that show it.

For owner review — Phase 1 deliverable, 2026-10-07 (Shubham Pitekar / shuence).

## What exists today

- `CurriculumStore` (`curriculum/store.py`): 29 `CREATE TABLE` statements (boards, academic_years,
  terms, grades, sections, subjects, books, chapters, topics, subtopics, calendars, holidays,
  timetable entries, allocations, leave, cover, scheduled lessons, ...). All SQL funnels through
  `_exec / _fetchone / _fetchall / _commit`; schema runs via `executescript`; rows materialized to
  dicts inside an RLock.
- `OperationsStore` (`operations/store.py`): 36 tables from 18 feature mixins (notifications,
  homework, learning, guardians, automations, reviews, marks, exams, grants, feeds, photos,
  practice, sign-in codes, question reviews, owners, progress, pilot agreement, erasure). Same
  four-helper funnel.
- Durability today: whole SQLite file snapshotted to GCS (`storage/snapshot_sync.py`, debounced,
  generation-guarded single writer). Two instances would overwrite each other's snapshots — this
  is why Cloud Run is pinned to `--max-instances=1`.
- Postgres is already reachable: `assessment/postgres_kv.py` holds a psycopg connection-pool layer
  (Cloud SQL unix socket via `/cloudsql`, pool per DSN, used by the JSONB stores: users, sessions,
  audit log, learner events).

## Portability audit (read, 2026-10-07)

The two stores' SQL is almost portable. Full inventory of SQLite-isms:

| SQLite construct | Where | Postgres translation |
|---|---|---|
| `?` placeholders | everywhere | `%s` (single regex on statement text; statements contain no literal `?`) |
| `INSERT OR REPLACE` | `operations/automations.py` ×2 (automation_runs, automation_school_runs) | `INSERT ... ON CONFLICT (<pk cols>) DO UPDATE SET ... = EXCLUDED....` |
| `PRAGMA table_info(t)` | `curriculum/store.py` `_migrate` ×8 | `SELECT column_name FROM information_schema.columns WHERE table_name=%s` |
| `PRAGMA journal_mode/busy_timeout/foreign_keys` | constructors | no-op / `SET statement_timeout`, `SET lock_timeout` |
| `COLLATE NOCASE` on TEXT (terms.name, sections.name + their UNIQUE constraints) | curriculum schema | `CREATE COLLATION nocase (provider = icu, locale = 'en-US', deterministic = false)` then `COLLATE nocase`; nondeterministic ICU collation gives case-insensitive equality, preserving the UNIQUE semantics |
| `executescript` | schema bring-up | small splitter (statements are static DDL with `;` terminators; comments stripped) — psycopg refuses multi-statement execute |
| `sqlite3.Row` → `dict` | helpers | psycopg `dict_row` |

Types (`TEXT`, `INTEGER`, `REAL`, ISO-8601 date strings) need no changes.

## Design

1. **One backend seam.** Both stores already funnel every statement through four methods. Add a
   `PostgresBackend` with the same four methods + `executescript(schema)`, and a store factory
   `ACOS_STORE_BACKEND=sqlite|postgres` (default `sqlite`). Local dev and tests stay on SQLite
   untouched; the full suite runs against both by running it twice (env var switch).
2. **One translation module** `storage/pg_backend.py`: placeholder rewrite, the COLLATE DDL
   translation, `PRAGMA table_info` rewrite, `INSERT OR REPLACE` rewrite, schema splitting. All
   translation in one tested unit (`tests/test_pg_backend.py`), no per-call-site changes.
3. **Connection**: reuse the `postgres_kv.py` pool (same DSN resolution, one pool per DSN,
   dict rows). Rehearsal runs connect with `PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE` to a
   scratch database; production uses the existing Cloud SQL socket env.
4. **Migration script** `scripts/migrate_snapshots_to_postgres.py`:
   - inputs: the two GCS snapshot objects (`curriculum-snapshots/curriculum.sqlite`,
     `operations-snapshots/operations.sqlite`) or local copies (owner rehearses on a copy of
     production data);
   - opens each read-only, creates the translated schema in Postgres, copies table-by-table in
     FK-safe order, prints per-table row counts from both sides and fails non-zero on any
     mismatch;
   - safe to re-run: each run truncates the target tables (FK order / `CASCADE`) and re-copies,
     so a partial run is repaired by running again;
   - writes a signed summary (counts + sha256 of each snapshot file) into the PR evidence.

## Cutover and rollback

- Deploy with `ACOS_STORE_BACKEND=sqlite` (behaviour unchanged). Rehearse migration on a copy of
  production data; commit the count-by-count evidence in the PR.
- Cutover window (outside school hours): freeze writes (maintenance flag or a short drain), take
  the final snapshot, run the migration script, verify counts, deploy with
  `ACOS_STORE_BACKEND=postgres`, watch logs/error groups.
- Rollback path: the flag flips back to sqlite and the container restores the last GCS snapshot —
  snapshot upload stays enabled for 7 days after cutover (belt and braces), then can be retired.
  A rollback loses at most the writes made between cutover and rollback; the runbook names the
  drain step that makes that window minutes.
- After both stores are on Postgres and the two-instance concurrency test passes (parallel writes
  to one school from two processes, row counts equal), raise `--max-instances` to 2 in
  `.github/workflows/deploy-gcp.yml`. Until both are moved, `--max-instances` stays 1.

## Risks and mitigates

- **Dialect surprises in rarely-run code paths** (the `_migrate` PRAGMA reads run only on schema
  drift): the suite on Postgres is the detector; the 8 PRAGMA sites are catalogued above.
- **Nondeterministic collation performance**: only two columns; indexed ICU equality is fine at
  this scale.
- **Transaction semantics**: the helpers hold the same RLock, so call-site semantics are unchanged
  from SQLite's serialized access.
- **Sequencing fallback**: if Phase 2 runs short, move `CurriculumStore` first (most writes from
  the most people) — the backend seam makes that a per-store env choice. Recommendation: move both
  in one cutover window; two cutovers cost more than one.
